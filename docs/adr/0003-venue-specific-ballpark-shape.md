# 0003. 守備配置圖依球場繪製外野輪廓：以官方全壘打牆距離重建,不使用球場平面圖

- Status: Accepted
- Date: 2026-09-16

## Context

ADR 0002 交付的守備配置圖(`FieldAlignmentDiagram`)使用一條寫死的外野弧線:

```
M 200 318 L 23 141 A 250 250 0 0 1 377 141 Z
```

無論比賽在芬威、PNC 還是道奇球場,畫出來的外野形狀完全相同。但棒球場是少數**每一座都不一樣**的職業運動場地——邊線長度、左右不對稱、中外野深度差異極大,而這正是球迷對一座球場的辨識依據。目前的通用弧線把這個特徵完全抹平。

需求是「根據球場不同畫出不同球場的外觀」。因此要先確認:**這些尺寸拿得到嗎?拿得到到什麼程度?**

## Decision

以 **`/api/v1/venues/{venueId}?hydrate=fieldInfo`** 提供的官方全壘打牆距離重建外野輪廓,並在 UI 上明確標示這是「依官方公布之全壘打牆距離繪製」,而非球場平面圖。

### 資料來源與可行性(已查證)

`fieldInfo` 提供最多 7 個角度的牆距離(英尺)與場地屬性:

| 欄位 | 內容 |
|---|---|
| `leftLine` / `left` / `leftCenter` | 左外野邊線 / 左外野 / 左中外野 |
| `center` | 中外野 |
| `rightCenter` / `right` / `rightLine` | 右中外野 / 右外野 / 右外野邊線 |
| `turfType` | `Grass` / `Artificial Turf` |
| `roofType` | `Open` / `Retractable` / `Dome` |
| `capacity` | 容量 |

PNC Park 的實際回傳(文件範例):`leftLine=325, left=389, leftCenter=410, center=399, rightCenter=375, rightLine=320`。注意 **`leftCenter`(410)比 `center`(399)更深**——這種不對稱正是畫出來會有辨識度的部分。

`game.venue.id` 已隨 `/schedule` 回應取得(`GameSchedule.venue`),`GameDetailPage` 也已在顯示 `venue.name`,取得場地 ID 不需任何額外工作。

> ⚠️ 撰寫本 ADR 的環境無法直連 `statsapi.mlb.com`(egress 政策封鎖),欄位依據為 `pseudo-r/Public-MLB-API` 文件與 `python-mlb-statsapi` 的型別定義(含上述 PNC 實際數值)。因此**所有幾何換算寫成 `src/utils/ballpark.ts` 的純函式並以單元測試鎖定**,且在 `fieldInfo` 缺漏或格式不符時一律退回原本的通用弧線,不讓資料問題變成破圖。

### 幾何模型(明確的簡化)

1. **角度指派**:以本壘為原點、中外野方向為 0°,兩條邊線為 ±45°,7 個命名點以 15° 等距分佈(`leftLine` −45°、`left` −30°、`leftCenter` −15°、`center` 0°、`rightCenter` +15°、`right` +30°、`rightLine` +45°)。真實球場的「左中外野」未必正好落在 15°,這是為了可預測性採取的建模選擇。
2. **比例正規化**:該球場最深的一點對應到 250 SVG 單位,其餘依比例縮放。**保留的是相對形狀,不是絕對大小**——跨球場比較「誰比較大」請看標示的距離數字,不要看圖。
3. **外野手站位改為依牆計算**:外野手節點放在該角度牆距離的 82% 處。這同時解決了短邊線球場中節點可能跑到牆外的問題,而且物理上也是對的——外野手站在牆前面。
4. **內野維持示意比例**:照實際比例畫,內野會小到看不清球員名字。內野、壘包與投手丘沿用現有座標,僅外野牆與外野手改為資料驅動。

### 明確不做的事(範圍邊界)

1. **不宣稱是球場平面圖**。這是 5–7 個角度的牆距離,用曲線串起來得到的是*合理形狀*,不是實際幾何。真實的牆由直線段與折角組成,樣條曲線會把它們抹圓。
2. **不畫牆高**。`fieldInfo` 根本沒有這個欄位。芬威的綠色怪物畫出來只會是一條短邊線,看不出它是一面高牆;瑞格利的常春藤、休士頓的 Crawford Boxes、PNC 的凹角同樣無法還原。
3. **不畫看台、屋頂結構或場館外觀**。`roofType` 僅用於文字標示。

## Alternatives Considered

1. **改用 Baseball Savant 的實際圍牆多邊形**
   - *否決理由*:Savant 的噴灑圖確實帶有各球場的真實圍牆座標,但 `baseballsavant.mlb.com` 並非開放 CORS 的端點,零後端架構取不到;且該資料未公開文件化,穩定性無保障。
2. **內嵌各球場的手繪 SVG 輪廓(30 份)**
   - *否決理由*:精確度最高,但需要人工維護 30 份向量檔並在球場改建時更新;打包體積與維護成本都與收益不成比例。本專案的定位是數據查詢,不是球場圖鑑。
3. **烤成靜態 `src/data/venues.json`(比照 `teams.json`)**
   - *部分採納,但本次不做*:球場尺寸確實是靜態資料,烤成本地檔可達成執行期零請求,完全符合既有模式。但**本環境無法連線驗證這 30 筆資料**,而產出一份無法驗證的靜態檔,比多打一次請求糟糕得多。本次採用執行期查詢(24 小時 staleTime,全聯盟僅 30 座球場),待資料實測確認後再烤成靜態檔是後續的純優化。
4. **各球場依實際尺寸採用統一絕對比例**
   - *否決理由*:多數球場最深點都落在 395–420 英尺,統一絕對比例與正規化的視覺結果幾乎相同,卻會讓短邊線球場的外野手節點落到牆外。改採正規化 ＋ 標示距離數字。

## Consequences

- **好處 (Pros)**:
  - 芬威、PNC、道奇球場點進去會是三種看得出差別的形狀,逐場頁具備「場所感」。
  - 外野手站位隨牆深淺調整,比固定座標更接近真實。
  - 幾何換算為純函式,可完整單元測試;`fieldInfo` 缺漏時自動退回通用弧線,不會破圖。
  - 額外成本極低:每座球場每 24 小時一次請求,全聯盟僅 30 座。
- **代價與風險 (Cons & Risks)**:
  - **這偏向質感而非功能**。它傳達的真實資訊是「這座球場邊線短/中外野深」,不會改變任何數據判讀。誠實標示其性質比畫得漂亮更重要。
  - 使用者若期待真實球場平面圖會落空,需靠 UI 文案管理期待值。
  - 每場比賽多一次 `/venues` 請求(可由後續烤成靜態檔消除)。
  - 春訓場、海外賽場地(如東京巨蛋)可能缺 `fieldInfo`,一律走 fallback。
  - 15° 等距的角度指派是建模選擇,與真實球場的實際角度有出入。
